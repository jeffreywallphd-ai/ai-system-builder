# Headless System Builder threat model

## Data window presentation

The Data instruction-isolation regressions run adversarial CSV text through the
actual provided-row worker and the approved input compiler. Selected text stays
data; unselected action/destination/system fields cannot change the recipe or
output root. Generation, model readiness, network connection and process launch
are denied by test spies and must have zero calls. Extra request authority fails
before source lookup. These deterministic feature checks use no model inference
and do not grant comprehensive roadmap qualification.

Security impact: security-relevant. Protected assets are saved source/version
metadata, transient task identity and current window consent. The fixed Data
intents accept exact opaque references, not paths, provider coordinates, data
rows or execution callbacks. Workspace and artifact-read authorization apply
before and after resource reads and at the existing display/context egress.

A task point-index must agree with its durable accepted owner and plan index,
organization, workspace, principal and host before any lazy processor access.
Reserved, issued, unknown and foreign tasks have no presentation authority.
Only display may cross the original client boundary under separate consent;
execution/status/review/save routes still require the original plan client.
Interactive details contain fixed text, finite state and bounded counts. The
connector context contains only view and exact identifiers. Revocation retires
delivery and context while preserving independently authorized Data work.

Focused tests cover strict schemas, stale or foreign lineage/version selection,
permission withdrawal, accepted-task proof before lazy access, review arrival
during a status read, replay and lease retirement. Packaged Desktop and managed
browser journeys cover the actual separately consented handoff. These checks do
not establish provider transfer, model quality or native worker/offload cleanup.

Authority: [ADR-0047](../adr/ADR-0047-headless-system-builder-delegation.md).
Scope: the approved desktop connector, shared authoring and receipt boundaries,
revocable window presentation, managed parity, and passive plan discovery. This is a design
review; the first contract alone does not qualify any live host.

## Approved provider source registration

The result-review query first proves the exact durable accepted task/actor/client/
host association and current artifact read permission. It exposes finite counts,
reasons and report/policy fingerprints, never rows, samples or paths. Strict host
and transport decoders reject foreign tasks, extra fields, getters and impossible
counts. Discovery cannot warm the processor or approve a result.

The opt-in v5 result-save step grants only the exact accepted task, quality report
and safe output name. Both app channels disclose immutable local saving with no
model calls or outside publication. Current plan revision/order, actor/client,
workspace role, artifact write permission and deadline are checked at reserve,
issue and final metadata commit. A private source/report/name digest excludes
only the owner's transient save-availability flag. A task-unique issue record
prevents competing plans from saving the same prepared result.

Artifact materialization stays outside retrying transactions. Version metadata
and the private causal receipt commit together. Unknown issue or commit retains
evidence and cannot admit another attempt. Lost commit acknowledgement allows one
read of the exact private save identity and source digest, never publication retry
or ordinary-version adoption. An already committed business result survives reply
loss; current authority independently gates disclosure. The ordinary approval
performer rechecks issued/unconfirmed ownership inside its task queue. Native
cleanup and stop proof remain separate; a metadata receipt cannot retire staging.

Explicit provided-column mapping is separate from legacy task `inputField`.
TS and Python require two distinct bounded columns, provided mode and omitted
context. Missing selected text cannot fall back to canonical aliases or unrelated
context. The mapping is retained in the admitted recipe/digest and immutable
lineage. It adds no generation, source format, destination or lifecycle authority.

The finite Data status read is restricted to plan-review registrations and the
current workspace artifact read policy. Desktop and Managed hosts recheck the
exact principal, organization, workspace and grant around the owning task read.
Foreign task records, revoked authority and missing access do not return task
metadata. Discovery does not enumerate tasks or initialize the Data feature.
Transport egress validates the exact task and finite state and count fields.
Extra source metadata, counter overflow, mismatched IDs and private diagnostics
fail closed. SDK tools are available only in plan-review mode. Synthetic host,
route and SDK checks do not qualify the complete live two-host Data journey.

Dataset metadata and comparison share this purpose-specific Data read boundary.
The application uses at most 16 exact sequential version point reads under the
existing workspace authorization. It verifies organization, workspace, version
and dataset ownership around each read. Duplicate or oversized requests fail
before storage. Missing or foreign records cannot become a partial reply.
The query never lists the organization or dataset history. Replies contain
bounded numeric facts and exact digests, with no source keys, private recipes or
documentation. Comparison uses the existing two-point, same-dataset owner.
Current authority is checked after each read and
before transport egress. Shared passive decoders reject extra fields, incorrect
targets, invalid ordering and inconsistent known split subtotals. These reads authorize
neither data generation, content export nor dataset publication.

The preliminary dataset input compiler accepts only passive local source
references and a provided-row recipe. Current trusted host, principal,
organization, workspace and artifact authority surround the exact point reads.
Completed task outputs must match their immutable snapshot identity, digest,
media type, size and private storage key. Duplicate sources, stale revisions,
unsupported formats and oversized inputs deny before a command is returned.
The preview exposes no filename, path, storage key or content, and describes
local file licensing as unknown. The private command preserves workspace
quality policy and requires output review. No model, runtime, provider,
publication is admitted by this helper. The plan-review-only
`data.preview-dataset-preparation` read exposes only the strictly reconstructed
matching preview. Both hosts check current artifact authority around the compiler
and before reply. Transport decoders reject private commands and extra fields,
changed source order, recipe, split, quality and effect limits. Discovery does not
initialize the compiler or runtime. A source-not-ready failure carries no private
diagnostics. This is metadata admission only; execution must still verify current
source bytes and approval.

The private local provided-row processing entry receives trusted admission
callbacks outside serialized request data. Its issuer must atomically bind the
exact plan, actor, sources and host-issued task ID; the method supplies no issuer
or public dispatch. Current authority surrounds exact source reads. Bounded owned
bytes, format, media, digest and local binding checks precede acknowledged issue.
General readiness may activate a runtime, so this path delays readiness until
that issuance. Final lifecycle fences prevent dispatch after host shutdown.
Local output and required quality review preserve existing policy. External
fallback, document parsing and model generation cannot enter this profile.
Unknown starts never authorize task lookup/cancellation or automatic retry.
Retained staging stays counted, including cleanup failures, until owned runtime
stop proof and confirmed retirement. Lost authority alone proves no worker exit.

Plan-review clients can propose one immutable Hugging Face source selected for
that client in the app. The version 3 preview declares required provider reads.
Both human decision channels display use of the saved provider access. The
proposal carries opaque task and file references, with no credential or private
provider path. The host reads the stored selection to resolve the source.

The plan owner checks current workspace permission, principal, organization,
client registration, approval revision, step order, selection and deadline.
Provider verification runs before publication. The commit transaction includes
the artifact catalog and backing, source snapshot, finalized task and this
plan step's private effect receipt. The synchronous commit fence also checks
source expiry and connection authority. The provider effect has a separate
namespace and key family. Replays verify this exact stored effect and source
with current permission and approval. An ordinary app import supplies no plan
receipt. Interrupted commits roll back all rows. An uncertain reply requires
an exact retry under current authority. No recovery adopts another plan's save.

The existing read, frame, queue, route and context bounds still apply. The effect
registers a remote source and its license declaration. Dataset localization,
preparation, publication and full native/browser Data journeys retain their
separate authority and qualification requirements.


The build-plan capability request uses the existing authenticated read
transport for one exact workspace. The desktop checks the current paired
editing grant and the application policy. The managed host checks the same
workspace permissions used by its existing editing operations. A reply lists
only eligible operations from the fixed saved-system catalog. Both hosts
check the shared edit scope again just before returning any action. The
reply leaves plan approval separate. Preview only reads scoped templates and
revisions. The audit log excludes proposed content.

The [presentation authority decision](../adr/ADR-0048-revocable-window-presentation-authority.md)
defines the new in-memory reservation, exact retry, and runtime bounds. Reject
agent self-acceptance, another interactive document, replaced workspaces,
incomplete revoke targets, expired leases and changed retry input. Recheck
current policy and document ownership after a held asynchronous check. The
reservation service owns only presentation state. It stores finite identifiers
and starts no runtime or provider. Actual renderer, transport, and native
window evidence still need their own checks.

The initial decoder accepts only known versioned read operations, a canonical
host incarnation and explicit resource targets. It rejects extra fields and
uses fixed failure codes. It operates on already bounded decoded data; a future
transport must enforce frame size, duplicate-field policy, identity and rate
limits before it dispatches any request. A well-formed request is never a
grant. The internal desktop dispatcher requires a grant returned by its
trusted caller and checks local identity, exact scope, current policy and
host shutdown state. It returns selected workspace, template and saved-system
metadata only. The internal credential adapter stores an organization-scoped
registry with at most 32 registrations. A pairing code has 256 random bits,
expires after two minutes, and is consumed after one completion or five
attempts. Bearer credentials have 256 random bits and expire after seven
days. Only domain-separated digests persist. The client ID is independent of
the digest, and remains stable while the same credential reconnects after a
desktop restart. Revoke removes the exact registration; it does not remove
any retry records. Unexpected persistence content or unavailable storage
denies admission. The test uses an isolated local SQLite database and no
actual user credential.

The authoring grant requires a new pairing with a separate native editing
confirmation. Older records and the original workspace-only request grant
read access only. The trusted pairing flow checks current workspace read and
write authority before issuing and exchanging an editing code. A pending
revoke fences in-flight grants immediately; an uncertain registry update
keeps that client denied until the host rereads saved state after restart.
The grant excludes all window control and privileged operations. The authoring
transport and its Settings entry point are wired separately.

The separately tested transport binds an OS-assigned port to literal
`127.0.0.1` and accepts only exact Host, no Origin or forwarding headers,
and POST to its two fixed paths. It accepts up to 8 KiB of compact UTF-8 JSON
and rejects non-round-tripping framing, including duplicate fields. Read
requires a verified bearer. Pairing completion can consume only a code
already issued by the interactive authority; it cannot begin pairing.
The caps are 16 connections, eight concurrent admitted requests, 128
admissions per one-second window, 8 KiB of headers, 128 KiB of response,
and a five-second I/O and shutdown wait. Shutdown fences new calls, closes
owned sockets and waits for admitted work; timeout is not proof of cleanup.
Desktop Settings starts the listener only after native confirmation from an
owned foreground window. Pairing validates the exact workspace and confirms
its current label and ID; the native dialog alone shows the code. The app
rechecks the exact foreground window and main frame during interactive
admission. Both start prompts tell the user that existing authorized clients
can reconnect once the shared listener starts. The preload
returns fixed outcomes and projects only the connector address and bounded
client metadata. Restart leaves the listener off; existing authorized clients
can reconnect after an explicit start with no new pairing. Closing the desktop
retires the listener before persistence. This does not grant write or window
control, or qualify packaged-host MCP delivery.

The internal edit decoder admits only exact add, configure, connect, move and
remove operations on a batch of 1–24 edits. It captures passive input before
parsing and binds the host incarnation, workspace, system, record revision and
composition revision. Apply additionally requires a preview digest and an
idempotency key. This shape check grants no permission; workspace access,
asset/configuration/placement policy and atomic writes remain application
responsibilities. No connector write operation is enabled by the decoder.
Asset versions are literal identifier values, including prerelease or build
metadata. Floating aliases, ranges and path forms are unavailable. The
application still has to resolve the exact version in the granted workspace.
The desktop admits up to four concurrent management operations. It fences and
drains them along with socket work before releasing persistence; a timed-out
drain remains pending for an explicit retry.

The stdio MCP adapter accepts a literal loopback HTTPS address, its current
certificate fingerprint, and a credential only from its trusted launcher.
The desktop makes a new in-memory certificate at listener startup. Native
pairing and Settings display the fingerprint. The adapter releases no HTTP
bytes until the same TLS socket proves possession of the pinned key. A stale
port or untrusted replacement listener receives no credential. It exposes
five strict read tools and cannot
receive a URL, credential, or arbitrary command through them. It uses no HTTP
proxy or redirect, limits four active forwards, limits each to five seconds
and 128 KiB of result, and validates fixed result fields before returning
them. The SDK bounds its stdio read buffer to 16 KiB; the adapter caps eight
unanswered requests, four pending writes and 256 KiB per response. It closes
on overflow. Incoming responses and unused notifications are discarded. An
initialization notification is admitted once and cancellation is bounded by
outstanding request IDs and actual response progress. The desktop tracks raw
sockets through TLS negotiation and destroys them on listener shutdown.
The in-memory pin protects against a different local listener,
not compromise of the app, trusted launcher or OS account. Client secret
enrollment, packaged host and managed delivery need separate qualification.

Managed parity must recheck existing OIDC, membership and row-security
authority, including for streams, receipts and worker replay. Neither synthetic
tests nor localhost timing qualify production deployment. Compromise of the OS
account or trusted host remains outside the protection claim. Revocation cannot
recall context already delivered. Rollback disables the connector and
presentation routes, invalidates their grants and preserves committed data,
ordinary UI access and evidence.
The read-only plan preview uses the shared proposal parser to validate the
ordered steps and exact host and workspace scope. The parser derives the
effects from the allowed operations and rejects additional authority data.
The preview fingerprint supports comparison. The application decision policy
requires the exact proposal, current revision, unexpired deadline and
host-verified human identity for the proposal's organization and workspace.
Whole-plan approval covers the bounded list. Individual approval can add only
the next step. A closed or revoked decision cannot be reopened. The host
must bind each channel to the same owned transaction and recheck the actor
and deadline before commit. This policy has no execution entry point.
The structured review repository uses the platform transaction owner and verifies
the stored proposal on every use. The organization, workspace, principal, agent
registration, host session and plan fingerprint select one record. Competing
decisions update the exact current revision. A proposal can receive decisions for
15 minutes. An exact retry preserves its first deadline. Each registered client
and workspace uses the existing maximum count for retained headless records.
The repository requires the host to authorize the operation in the transaction
and checks that the request remains current at commit. Desktop and managed hosts
must still bind this repository to verified approval channels.
The step execution adapter rechecks the exact decision revision and reads the
operation from the saved proposal. It requires an approved step and matching
operation receipts for all earlier steps. The receipt key binds the host,
proposal and step number. An ordinary save cannot satisfy that check. A new
effect and a change to the approval both update the same private fence under
their owned transaction. A fence conflict or an expired actor rolls back the
effect. Saved changes and their receipts still commit together. The pinned
desktop connector uses this adapter. The request selects a proposal and step
by reference. Only the verified plan record supplies the operation and input.
The connector sends a successful result while the desktop transaction owner
still holds the exact current approval. A decision withdrawn before the reply
withholds the result. The already committed effect remains in the journal.
The portable desktop client forwards only the step reference. It validates
the exact receipt and reports an uncertain reply without issuing a second
request. Managed execution uses its own current approval and delivery checks.
The approval list contains at most 32 live proposal references for one
app user, workspace and host session. Listing requires current access to
that exact scope. The index and review record share the owned transaction.
The list omits expired requests and removes cancelled, denied and revoked
requests. The durable review record keeps the outcome and original deadline.
The desktop approval service takes the human channel and current caller from
the trusted host adapter. It derives organization and principal from the
local profile. Opening or deciding a proposal checks the matching live
plan-review registration and workspace membership under the transaction.
The service uses the same live registry as the connector. Its requester
check detects revocation or expiry before commit and when returning results.
The desktop approval bridge accepts fixed messages from a trusted current
window. Popup and chat use separate open, dismiss and decision messages.
The native handler fixes the approval channel. The request body and chat
text cannot choose it. A decision requires the exact view issued to that
window and channel. The view binds workspace, requester, plan fingerprint
and displayed revision. The bridge checks the canonical fingerprint before
sending the view. Only a successful reply issues a one-use view ID.
Reopening retires the previous ID for that channel. Closing a view retires
its exact ID. A decision from either channel advances the same durable
revision, so a stale view in the other channel cannot overwrite it.

Desktop attaches the bridge in its focused, visible, owned main window.
Settings offers a popup and an approval conversation for the selected
workspace. Both show the exact saved-system effects and require an explicit
choice. Closing a view or switching workspaces discards late replies and
asks the native handler to retire that view. When main processes retirement,
an uncommitted decision loses its view authority. A committed decision
remains in the saved plan. Preload exposes only the fixed operations and
bounded results.
Desktop plan-review credentials use a distinct pairing mode. A current
registration can request plan review only when the host provides that
capability. It carries no direct editing, conversation or window-control
grant. The desktop host keeps the mode unavailable until it wires the plan
route and its policy.
The optional desktop plan-review route accepts only proposal submission and
status reads with the dedicated grant. It rechecks the registered client and
workspace before dispatch and checks both current authority and the plan
deadline before sending a successful result. It bounds the body and validates
the exact status result. Agent requests cannot carry a decision or use the
existing edit routes with this grant. The desktop composition binds the
route to the current app policy and platform transaction. New proposals
resolve exact immutable saved sources inside the owned write. An authorized
retry can read its original proposal even after a source changes. Later
execution still needs a current revision check. Desktop startup connects the
route and app approval service only when it has the platform transaction owner.
The Desktop MCP plan-review mode uses the pinned connector to submit and
check plans and run the next approved step. Direct editing, conversation
sending, and window control require a separate grant. The Desktop host
checks the dedicated registration, exact proposal and current workspace
policy. Its SQLite owner serializes the successful reply with current
approval and workspace access.

The managed host optionally accepts proposals and reads their status through
a third exact issuer-verified OIDC client registration. Startup rejects
duplicate identifiers. The server recognizes the configured client from
the verified token's signed client ID or authorized party before applying
organization policy. That client is confined to exact headless read,
plan-review and plan-step routes even when the signed token omits the
access-token type. Plan requests still require an unambiguous typed access
token.
Ordinary edit, approval, and window routes do not
accept this credential even when its user has a writer role. The authoring and
browser registrations cannot stage a proposal for the plan client.
The managed plan-review route accepts only a bounded passive proposal or
fingerprint. The owning transaction rechecks
organization membership, the active workspace and exact saved revisions
before inserting a proposal. The result contains only the exact fingerprint,
approval progress and expiration. Proposal submission cannot record a human
decision or execute a change.

The managed plan-step route accepts the exact plan fingerprint, approval
revision and next step number. It uses only the saved operation. The
owning transaction saves the change and its retry receipt together. Before
sending a successful reply, PostgreSQL holds point-read locks on the
permission and approval records. The server sends at most one reply for
that request. A failed or withdrawn reply does not authorize a new key.

The managed browser has separate fixed approval routes for its popup and
signed-in approval chat. Both require the configured HTTPS origin, a
verified browser registration, and a live proof tied to the exact browser
document and credential. The route fixes the channel internally. Text from
the chat client or model has no approval authority. The plan transaction
checks the organization, signed-in principal, active workspace, and
current membership.

Each browser document can hold one open approval view per channel. The
global limit of 32 views covers both channels. A view binds the exact
channel, requesting client, plan fingerprint and displayed revision. A
decision consumes its view once. Reopening or closing that view, losing
document access, expiry, or a change to the saved revision denies a late
decision. Both routes use the same saved approval and its revision. A
decision in one channel can retire a stale choice in the other. The
browser routes carry no operation payload to execute.
The internal operation store partitions receipts by verified organization and
hashes the complete principal, client, workspace, operation and key scope.
Receipts hold a fingerprint and the minimum saved revision reference; change
entries hold only workspace-scoped system and revision identifiers and a
sequence. The store checks the host's synchronous authorization fence
around its transaction and replays. The application must separately check
current resource authority before lookup and before any response leaves the
host. After result expiry the retained key stops another write; capacity
exhaustion and unknown outcomes require reconciliation.
The optional authoring route uses the same pinned literal loopback listener
and frame limits. It accepts only the finite authoring contract and requires
an explicit writer grant for the exact workspace. Before the response, it
rechecks current registration and its synchronous grant fence. The response
admits only fixed errors, bounded preview consequences, and saved revision
references. This adapter does not activate the authoring route by itself.
Desktop authoring rechecks the existing organization policy and saved
workspace status inside the owning SQLite transaction, using the same
platform and organization views as the application. This prevents an earlier
authorization result from surviving a workspace or membership change that
commits first. The outer admission and response still check live policy.

The read-only saved-system feed authenticates opaque cursor tags with a private
host-incarnation key. Tags bind the organization, workspace, registered client
and sequence. A cursor is never authority: snapshot and replay recheck the
current paired grant and workspace policy before returning data. Cross-scope,
old-host or retired cursors require a new snapshot. Results are bounded saved
references and status; the feed never carries draft data, secrets or UI state.

The managed saved-state polling routes require the current OIDC bearer and
verified organization context. They use existing workspace authorization before
and after reading saved data, check token lifetime again before the response,
and bind signed cursors to the current principal, organization, workspace and
worker. The exact routes accept up to 1 KiB of compact JSON and at most 16
active requests per worker after authentication. Request-body reads have a
five-second limit. Responses are at most 128 KiB
and must not be cached. The transport has no authority to request window
context or send presentation actions. The stream uses the same authorized replay
read for each page, one read at a time. It closes after 15 seconds, any loss of
authority, disconnect, shutdown, or backpressure. Up to eight streams share the
16-request cap. Events are bounded to 32 KiB and sent at most every 500 ms.
An out-of-scope cursor returns a fixed resynchronization event and ends the stream.
Browser and cross-worker delivery qualification remain separate.
The snapshot reads only indexed active summaries scoped to one workspace and
applies a 129-row SQL cap. Passive route and workspace checks retain the same
policy. Success adds no audit row. Failed authorization uses one content-free
count sample per minute per worker, with one pending log write at most.

The managed OIDC verifier supplies the optional access-token client identifier
only after verifying the signed issuer, audience and typed access token. It
checks the credential's exact lifetime and accepts a bounded claim. A caller's
headers, payload and scope names cannot supply this identity. The identifier
stays in server authorization context. It grants no feature permission by
itself, and browser document ownership requires separate evidence.

The thin client treats saved-state checkpoints as bounded passive data and
keeps credentials and cursors out of URLs. The same tab and connection
ownership guards both the notification and the data reads it starts.
Late results after hide, detachment, resync or replacement do not update
the view. An authoritative list that omits an open system preserves the
existing on-screen copy and does not enable saves or builds against it.

The managed headless client policy requires distinct configured registrations
for agent and interactive browser requests. It refuses caller-declared
roles, missing or ambiguous organization selection, mismatched principals
and expired bindings. Client classification only identifies the credential's
purpose. Operations still require current application policy, and the
target document must hold separate user consent before it can show agent work.

The managed stdio adapter uses the configured exact HTTPS origin, organization
and workspace. A tool cannot choose its own destination or credentials.
The adapter verifies the server certificate, uses fixed paths, refuses
redirects and retains the request and result bounds. It treats a missing
reply from a write as unconfirmed. Desktop certificate pinning still applies
when the adapter runs in desktop mode.

The browser document registry binds the exact host, workspace, authenticated
principal, verified browser bearer and random document proof. The verifier
compares per-verifier keyed digests in constant time. It keeps the comparison
private to the server and excludes the digest from the authentication context
that downstream code can serialize. A second valid bearer from the same client
cannot renew or retire the document. The registry bounds document slots and
policy reads. Expiry, loss of workspace access and explicit retirement end the
document's authority. A replacement worker requires a fresh registration and
consent.

Managed consent uses the same exact-window request and lease rules as desktop.
An admitted agent request can target only the same principal and organization
in an authorized workspace. The browser must prove ownership of its own
document to observe, grant, activate or revoke. A request-scoped fence stops
held authorization from creating a prompt or changing a lease after the
request retires. The admitted attempt uses the registration lifetime across
individual calls. This composition does not consume or send presentation
content.

The browser consent route is disabled until a managed operator supplies an
exact HTTPS frontend origin. Browser same-origin fetch metadata and exact
origin are additional transport checks. OIDC, organization membership,
workspace permissions and document proof establish caller authority.
Document proof travels by header after registration, and the route applies
strict JSON, request size, deadline and concurrency limits. An expired
request cannot return a consent response. Results must match the exact host,
requested workspace or browser document, and requested attempt or lease.
Desktop context challenges are excluded from this consent-only path. The server retires the route and
its document authority before draining its persistence.

The thin client keeps the short-lived document proof in one page instance.
It sends the proof only to the fixed same-origin consent route and keeps it
out of durable storage and the URL. The local controller retires consent
before waiting for a revoke response. Credential changes, page exit, tab
visibility and workspace selection fence late responses. The UI sends a
best-effort retirement using the original credential when it remains current.
Temporary registration capacity is reported separately from access denial.
The browser retries transient responses with one outstanding registration and
capped backoff. A dormant document remains detached until the page returns.
Passive observations go through a separate exact route and the same membership
and workspace policies. Only that read-only route uses the bounded denial
sampler and omits successful audit records. Consent changes keep standard audit.

The managed stdio consent tools use a distinct opt-in and a fixed agent route
with the same OIDC and current workspace policy. Each connector process sends
one random session reference. The server derives the prompt's public session
ID from a private, process-local key so the prompt cannot disclose the request
reference. Browser credentials cannot initiate requests. The agent cannot
accept consent. Each successful reply must match the exact requested host,
workspace and window or attempt. The host checks the current public session,
task and exact lease. The connector suppresses any response that echoes its
private session reference. Listing and requesting grant no right to
deliver content.

Optional managed presentation discovery also requires a separate local connector
setting. The server must enable delivery for the verified agent route. Renew
responses must match the submitted lease, presentation receipts must match
the command ID, and fresh context has a final current-lease check on the server.

Managed presentation uses the existing 32-command, 256-receipt lease queue.
The command lane verifies the live lease and current resource authorization
before returning display metadata. It bounds concurrent policy and resource

## Approved local dataset task boundary

Plan v4 is an explicit host capability. Strict DTOs reject source paths, raw rows, chosen runtime IDs, generation settings and extra destinations. A source-save step cannot be combined with preparation of the same upload at an invented future revision. The UI reconstructs and verifies the fixed processing limits for both approval channels; it distinguishes starting work from approving or saving results.

Durable reserved/issued/accepted records bind the exact organization partition, actor, registered client, host incarnation, plan fingerprint, approval revision, step and source/command digests. Acknowledgement loss, incomplete records and races cannot provide a second issuance. Accepted business receipts survive later outward revocation; final publication still requires current authority. Status uses exact accepted indexes and current artifact-read permission, with no enumeration, unknown-task adoption, result materialization or output payloads. Host-exit recovery is not claimed.
